# P005 — Scheduled Wake Feasibility

## Finding

P005 establishes no supported way for a normal userspace timer or launchd calendar job to wake the target iPad mini 2 from a suspended or system low-power state. `scheduled_wake` therefore remains **UNVERIFIED**, `scheduled_wake_validated=no`, and `wake_guarantee=no`. No wake alarm command or backend is implemented.

The P004 scheduler is a different capability. It evaluates schedules and can request a bounded assertion only while `ios-caffeinated` is running. Both schedule execution on the target and the real IOKit assertion effect still require hardware validation. P004's `IOKit_RUNTIME_UNVERIFIED` label is intentional: finding an IOKit symbol or compiling an iOS-target binary does not show that an iOS 12 device exports or honors that API.

This is a source and SDK feasibility result, not a device result. At the time of this P005 report, the iPad was unavailable and no hardware experiment had been run. Later assertion observations do not establish scheduled wake; see [P010 hardware findings](P010-HARDWARE-FINDINGS.md).

## Evidence labels

- `EVIDENCE_SUPPORTED`: primary documentation or source directly supports the stated behavior.
- `EVIDENCE_UNSUPPORTED`: the documented interface does not provide the behavior needed for scheduled wake.
- `UNVERIFIED`: private behavior, iOS 12 target availability, A7 hardware behavior, or runtime effect is not established by available evidence.
- `NOT_APPLICABLE`: the mechanism cannot operate in the state being discussed.

Labels apply to the requested scheduled-wake behavior on the target. An API documented for macOS is not iOS evidence.

### Interpretation

1. **Can a normal userspace timer wake the iPad?** No supported path was found. It can request future process work only while its process/kernel timer context is serviced; it cannot promise that the device leaves a suspended or deep-idle state.
2. **Can launchd be relied on to wake it?** No. Its documented calendar/interval behavior is to run a missed job after the computer next wakes. The iOS 12 target daemon behavior still needs measurement.
3. **Is there a usable system/RTC wake mechanism on iOS 12?** No public iOS 12 API or A7-specific evidence was found. Apple's macOS power-event API and private powerd/RTC path do not establish iOS availability. A private target route remains an open question, not an implementation.
4. **Does jailbreak root access change this?** It may permit inspection or calls unavailable to a sandboxed app. It does not prove an iOS export, entitlement, kernel client permission, supported hardware alarm, or reliable delivery.
5. **What remains unverified?** P004 IOKit assertion availability/effect; whether this daemon is suspended; what low-power state the target enters; whether any private system alarm API is exported and authorized; whether LAN, Tailscale, or a particular system event resumes userspace.
6. **What observations are next?** The staged, bounded experiments in [P005 device test](P005-DEVICE-TEST.md). In particular, a marker observed only after manual unlock does not prove autonomous wake.

## Capability boundary and interface

P005 keeps three capabilities distinct:

- **Timed Awake**: a bounded direct request to inhibit idle sleep. Code exists, but the iOS backend is not hardware-validated.
- **Scheduled Awake**: the running P004 daemon evaluates persisted schedules and acquires an assertion for an active window. It cannot evaluate while it is not running.
- **Scheduled Wake**: an independent platform/hardware wake at a requested time. It remains `unverified`; P005 provides no `wake set` or alarm command.

`ic wake status` (the same CLI as `ios-caffeinate wake status`) prints compile-target/backend identity and static capability evidence. It does not connect to the daemon, read or write schedule state, resolve IOKit symbols, acquire/release an assertion, or alter power state. `runtime_wake_probe=unavailable` and `read_only_evidence=none` mean no read-only target wake facility is probed by this command. The report deliberately says `scheduled_wake=unverified` and `wake_guarantee=no` on every target.

The P004 missed-occurrence policy remains: missed windows are skipped; the daemon does not replay them, auto-reschedule wake attempts, or loop indefinitely.
